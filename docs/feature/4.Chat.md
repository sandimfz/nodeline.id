# Fitur Realtime Chat (Admin ↔ User) — Checklist & Keamanan API

Fitur ini belum ada di backend nodeline.id — dokumen ini rancangan baru yang menyambung ke sistem auth (JWT access token + role `user`/`god`) yang sudah ada.

---

## 1. Keputusan Arsitektur

### 1.1 Realtime transport
- **Socket.IO di atas NestJS** (`@nestjs/websockets` + `@nestjs/platform-socket.io`), namespace terpisah misal `/chat`.
- WS server **tidak bisa** lewat pola BFF proxy Next.js yang dipakai untuk REST (Route Handler itu request/response biasa, bukan koneksi persisten). Artinya browser **connect langsung** ke Nest WS server, bukan lewat Next.

### 1.2 Masalah turunan: browser connect langsung ke Nest, padahal token disimpan httpOnly di domain Next (BFF)
Karena pola auth kita menyimpan access token sebagai cookie httpOnly di sisi Next (bukan di localStorage/JS), browser tidak punya cara "biasa" untuk membuktikan identitas ke Nest WS server. Ada 2 opsi:

**Opsi A — Ticket Exchange (direkomendasikan, lebih aman)**
- [ ] Buat Route Handler `POST /api/chat/ticket` di Next (server-side, baca cookie `nl_access` yang httpOnly).
- [ ] Route Handler ini memanggil endpoint baru di Nest: `POST /api/v1/chat/ws-ticket` (butuh `Authorization: Bearer <accessToken>`) → Nest generate **tiket sekali-pakai**, umur pendek (±30 detik), disimpan di cache (Redis/in-memory) berisi `{ userId, role }`.
- [ ] Next mengembalikan tiket ini ke client (bukan JWT asli).
- [ ] Client konek socket.io dengan `auth: { ticket }`.
- [ ] Nest WS Gateway validasi tiket saat handshake, tiket langsung dihapus setelah dipakai (one-time use), lalu socket di-attach ke `userId`/`role`.
- [ ] Kalau tiket invalid/expired/sudah dipakai → tolak koneksi (`disconnect`).

**Opsi B — Shared cookie domain (lebih simpel, cocok kalau FE & BE 1 domain root, mis. `app.nodeline.id` & `ws.nodeline.id`)**
- [ ] Set cookie `nl_access` dengan `Domain=.nodeline.id` (bukan host-only) supaya ikut terkirim ke subdomain WS server juga.
- [ ] Nest WS Gateway baca & verifikasi JWT langsung dari cookie handshake (`socket.handshake.headers.cookie`).
- [ ] Trade-off: Nest jadi ikut "melihat" JWT asli (masih httpOnly dari sisi JS, jadi tetap aman dari XSS, tapi arsitektur BFF jadi tidak 100% murni).

> Pilih salah satu dan konsisten dipakai di seluruh alur; checklist di bawah menganggap **Opsi A** kecuali disebutkan lain.

### 1.3 Scaling (opsional, kalau > 1 instance Nest)
- [ ] Pasang Redis adapter (`@socket.io/redis-adapter`) supaya broadcast antar-instance tetap sinkron.
- [ ] Simpan mapping `userId → socketId[]` di Redis (bukan memory lokal) kalau multi-instance.

## 2. Data Model

- [ ] `Conversation { id (uuid), userId, assignedAdminId?, status: 'OPEN'|'CLOSED', lastMessageAt, createdAt, updatedAt }`
- [ ] `Message { id (uuid), conversationId, senderId, senderRole: 'user'|'god', content, attachmentUrl?, readAt?, createdAt }`
- [ ] Index: `Message.conversationId + createdAt` (buat pagination cepat), `Conversation.userId` (buat cek "punya user ini")
- [ ] `id` pakai UUID, **jangan** sequential integer (cegah enumeration/tebak ID percakapan orang lain)

---

## 3. REST Endpoints (histori, bukan pesan realtime)

| Method | Path | Role | Deskripsi |
|---|---|---|---|
| POST | `/api/v1/chat/conversations` | user | Buat/ambil percakapan aktif milik user (1 user idealnya 1 conversation OPEN) |
| GET | `/api/v1/chat/conversations` | god | List semua percakapan (filter status, sort by `lastMessageAt`) |
| GET | `/api/v1/chat/conversations/:id/messages` | user (pemilik) / god | Histori pesan, paginated (`cursor`, `limit`) |
| POST | `/api/v1/chat/conversations/:id/read` | user (pemilik) / god | Tandai pesan terbaca |
| PATCH | `/api/v1/chat/conversations/:id/close` | god | Tutup percakapan |
| POST | `/api/v1/chat/ws-ticket` | user & god | Terbitkan tiket sekali-pakai untuk handshake WS |

- [ ] `GET .../messages`: **anti-IDOR wajib** — cek `conversation.userId === req.user.id` ATAU `req.user.role === 'god'`, kalau tidak → `403` (pola sama persis seperti `orders/:id/items/:orderItemId/content` di fitur marketplace)
- [ ] Response error pakai format standar NestJS yang sudah ada: `{ statusCode, message, error }`

## 4. WebSocket Events

**Client → Server**
- [ ] `conversation:join` `{ conversationId }` — server validasi kepemilikan sebelum `socket.join(room)`
- [ ] `message:send` `{ conversationId, content, tempId }` — `tempId` untuk optimistic UI di client
- [ ] `typing:start` / `typing:stop` `{ conversationId }`
- [ ] `conversation:leave` `{ conversationId }`

**Server → Client**
- [ ] `message:new` `{ message }` — broadcast ke room setelah pesan tersimpan di DB
- [ ] `message:ack` `{ tempId, message }` — konfirmasi ke pengirim (reconcile optimistic message)
- [ ] `typing:update` `{ conversationId, userId, isTyping }`
- [ ] `conversation:closed` `{ conversationId }`
- [ ] `presence:update` `{ userId, online: boolean }` (opsional)
- [ ] `error` `{ code, message }` — dipakai kalau `message:send` ditolak (validasi, rate limit, dsb)

## 5. Checklist Backend (NestJS Gateway)

- [ ] `ChatGateway` pakai `WsJwtGuard` custom (validasi tiket di `handleConnection`, bukan per-event)
- [ ] Simpan pesan ke DB **dulu**, baru broadcast (jangan broadcast optimis sebelum tersimpan — kalau DB gagal, client lain jangan lihat pesan hantu)
- [ ] `conversation:join`: cek ownership setiap kali join (jangan asumsikan sudah tervalidasi dari handshake — user bisa saja coba join conversation orang lain)
- [ ] Auto-assign `assignedAdminId` ke admin pertama yang membalas (kalau belum ada), atau biarkan null (semua admin lihat semua — sesuaikan kebutuhan bisnis)
- [ ] Validasi `content`: tidak boleh kosong, panjang maksimal (mis. 4000 karakter)
- [ ] Simpan `senderRole` dari data user yang terverifikasi di socket (bukan dari payload client) — cegah user klaim jadi admin
- [ ] `handleDisconnect`: bersihkan mapping `userId → socketId` dari registry/Redis

## 6. Keamanan API — Checklist Khusus

- [ ] **Autentikasi handshake**: tiket sekali-pakai, umur pendek (≤30 detik), sekali pakai lalu dihapus dari cache — jangan pernah kirim JWT asli lewat query string (query string sering ke-log di proxy/reverse-proxy)
- [ ] **Re-validasi per event, bukan cuma saat connect**: cek ulang kepemilikan conversation di setiap `message:send` / `conversation:join`, jangan percaya cache hasil validasi handshake selamanya — koneksi socket bisa hidup lebih lama dari masa berlaku access token (15m), jadi status user (role berubah, dibanned, sesi dicabut) harus bisa terdeteksi meski socket masih "connected"
- [ ] **Revocation propagation**: kalau terjadi refresh-token-reuse-detection (semua sesi dicabut, sesuai logika di fitur auth) atau user logout eksplisit → cari semua socket aktif milik `userId` dari registry, **force-disconnect** saat itu juga. Jangan andalkan token expiry alami (15m) sebagai satu-satunya mekanisme cabut akses
- [ ] **Otorisasi berbasis role di server, bukan di client**: jangan pernah percaya field `role`/`isAdmin` yang dikirim dari payload client — role diambil dari data user yang sudah terverifikasi lewat JWT/tiket
- [ ] **Anti-IDOR**: `conversationId` dari client selalu di-cross-check ke DB (`conversation.userId === socket.data.userId` atau role `god`), sama seperti pola `content` endpoint di fitur marketplace
- [ ] **Rate limiting**:
  - [ ] Per-socket: maksimal N pesan / 10 detik (cegah flood/spam chat)
  - [ ] Endpoint `POST /chat/conversations` (buat percakapan baru): rate limit supaya 1 user tidak bisa spam bikin banyak conversation
  - [ ] Endpoint `ws-ticket`: rate limit juga (cegah brute-force pattern di endpoint auth-adjacent)
- [ ] **Validasi & sanitasi input**:
  - [ ] Batasi panjang `content` (mis. ≤4000 karakter) di DTO backend (`class-validator`)
  - [ ] **Selalu treat pesan sebagai plain text saat disimpan** — jangan simpan/eksekusi HTML apapun
  - [ ] Di frontend, render pesan sebagai text node biasa (React otomatis escape), **jangan** pernah pakai `dangerouslySetInnerHTML` untuk isi chat — ini mencegah stored XSS
- [ ] **Lampiran file (kalau dipakai)**: reuse endpoint `POST /storage/upload` yang sudah ada (kompresi sharp + whitelist tipe file), jangan bikin jalur upload baru yang belum divalidasi
- [ ] **CORS / WS origin allowlist**: `cors.origin` di Socket.IO config diisi domain frontend yang eksplisit, **jangan** `*`
- [ ] **Transport**: wajib `wss://` (TLS) di production, tidak ada fallback ke `ws://` plain
- [ ] **Payload size limit**: set `maxHttpBufferSize` Socket.IO (cegah DoS lewat payload besar)
- [ ] **Batas koneksi**: limit jumlah socket connection concurrent per `userId` (cegah 1 akun buka ratusan tab/koneksi sekaligus)
- [ ] **UUID untuk semua ID** (conversation, message) — cegah enumeration
- [ ] **Audit log** untuk akses admin: catat admin mana yang membuka/membalas conversation mana (dipakai pola sama seperti `audit_logs` di fitur payments) — penting untuk akuntabilitas kalau chat berisi data sensitif user
- [ ] **Privasi presence**: jangan expose status online semua user ke siapa saja — cukup relevan ke pihak yang terlibat di conversation yang sama
- [ ] **Minim logging isi pesan** di server log (log metadata seperti `conversationId`, `senderId`, timestamp — bukan isi pesan mentah) untuk mengurangi risiko kebocoran data lewat log
- [ ] **Retensi data**: tentukan kebijakan berapa lama histori chat disimpan, terutama kalau ada data pribadi/pembayaran yang dibahas di chat

## 7. Checklist Frontend (Next.js + TanStack Query + socket.io-client)

- [ ] Install `socket.io-client`
- [ ] `features/chat/socket.ts` — buat 1 instance socket per session (bukan re-create tiap render), ambil tiket dari `/api/chat/ticket` (Route Handler Next) sebelum `io.connect()`
- [ ] Auto re-ticket saat reconnect: kalau socket disconnect (mis. token/tiket lama expired), ambil tiket baru sebelum reconnect — jangan reuse tiket lama (memang sekali pakai)
- [ ] `features/chat/api.ts` — REST: `getConversations()`, `getMessages(conversationId, cursor)`, `markRead(conversationId)`
- [ ] `features/chat/hooks.ts`
  - [ ] `useConversations()` — `useQuery` (admin) / `useMyConversation()` (user)
  - [ ] `useMessages(conversationId)` — `useInfiniteQuery` untuk histori (scroll ke atas load lebih lama)
  - [ ] `useChatSocket(conversationId)` — subscribe event `message:new`, saat event masuk → `queryClient.setQueryData` append ke cache infinite query (jangan `invalidateQueries` biar tidak refetch semua & flicker)
  - [ ] `useSendMessage()` — optimistic update: push pesan sementara (`tempId`) ke cache dulu, ganti dengan data asli saat dapat `message:ack`, rollback kalau dapat event `error`
- [ ] Prefetch di Server Component: halaman `/chat` (user) atau `/admin/chat/[conversationId]` (admin) — prefetch `getMessages` (page pertama) via BFF, sama pola seperti fitur profile (server baca access token dari cookie, panggil Nest, `dehydrate` → `HydrationBoundary`)

  - [ ] `typing-indicator.tsx`

  - [ ] Admin: daftar percakapan (`conversation-list.tsx`) dengan indikator ada pesan baru, update realtime tanpa refresh

## 8. Edge Cases

- [ ] User buka chat di 2 tab sekaligus — pastikan kedua tab dapat `message:new` yang sama (karena 1 `userId` bisa punya banyak `socketId`)
- [ ] Access token expired saat socket masih connected lama — tiket WS harus di-refresh berkala (mis. setiap 10 menit reconnect dengan tiket baru), bukan cuma sekali di awal
- [ ] Admin menutup conversation (`status: CLOSED`) saat user masih mengetik — kirim event `conversation:closed`, disable input di client, beri opsi user untuk buka conversation baru
- [ ] Kirim pesan saat offline (socket disconnected) — jangan silent fail, tampilkan status "gagal terkirim, coba lagi" per pesan, biarkan user retry
- [ ] Percakapan lama tanpa admin membalas — pertimbangkan status/label tambahan seperti `WAITING` di UI admin (opsional, di luar 3 status inti)
